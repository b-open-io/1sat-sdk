# n0001 cutover: Node cluster host, accounts, 1sat.name paymail

Status: **Phases 0-3 done 2026-09-03 ~03:00 UTC; Phase 4 (retire forks) pending**
Date: 2026-09-02

Done: cli 0.0.104 installed in `~/Code/1sat-cli` (not `~/Code/1sat-cli`);
`wallet-host` x4 cluster on 8100 (Node 22.23.1) and the Node `wallet-monitor`
are in `~/pm2/wallet.config.js` and `pm2 save`d; nginx `wallet_backend` is
`server 127.0.0.1:8100` only, hash removed. The four bun forks on 8101-8104
are still running but receive no traffic. Found on the way: `StoragePg` used a
bare `require('pg')`, fine on Bun, fatal on Node 22 → wallet-node 0.0.72.

Goal: replace the four `bunx @1sat/cli@0.0.98 serve` forks (8101-8104, nginx
identity-key hash) with one pm2 cluster app running the Node build on 8100,
ship the account registry + per-domain paymail, and do it without dropping
wallet, paymail, or messagebox traffic.

## Why it can be zero-downtime

- **Same schema.** No `storage-pg` DDL changed since 0.0.98; `migrate()` on
  boot is idempotent (knex_migrations table). Old and new workers can share
  `account_wallet`.
- **Same sessions.** `RedisSessionManager` is unchanged since 0.0.98, so a
  BRC-104 session opened on an old worker is valid on a new one and vice
  versa. 72 sessions live in Redis today.
- **Free port.** `server.port` is 8100 and nothing listens there; the old
  forks use `ONESAT_PORT` 8101-8104. The cluster can come up beside them.
- **nginx reload is graceful.** Adding/removing upstream servers is a
  `reload`, not a restart.
- **Additive tables only.** The new code creates `accounts` in the messagebox
  database; the old code never looks at it. Registration (`/account/register`)
  should not be exercised until the old workers are out of the upstream,
  because the hash could send a client to a worker that lacks the route.

Only the monitor has a gap (seconds), and it is idempotent on restart.

## Phase 2 — bring up the cluster beside the old forks

Process definitions live in `~/pm2/wallet.config.js` (it reads
`~/.1sat/cli/wallet.env` into `env`, so the password never sits in the file).
Add one app to `apps`, leaving the five existing entries untouched:

```js
{
  name: "wallet-host",
  script: "/home/gorillapool/Code/1sat-cli/node_modules/@1sat/cli/dist/cli.js",
  args: "serve",
  interpreter: "node",
  exec_mode: "cluster",
  instances: 2,
  max_memory_restart: "1G",
  env: {
    NODE_ENV: "production",
    PATH,
    ...walletEnv,
    // no ONESAT_PORT: every worker shares server.port (8100)
  },
},
```

```bash
# Start only the new app; the running forks are not touched. First worker
# alone, so table creation (accounts, paymail_pending, messagebox) cannot race.
pm2 start ~/pm2/wallet.config.js --only wallet-host   # starts 2 workers per the file
# If you prefer to be strict about the race: set instances: 1, start, verify, then
# `pm2 scale wallet-host 2` and set instances back to 2 in the file.
pm2 logs wallet-host --lines 30   # expect: host listening on 127.0.0.1:8100 (accounts: on, paymail users: 1sat.app)
```

Verify directly on 8100, bypassing nginx:

```bash
curl -s localhost:8100/openapi.json | head -c 200
curl -s -H 'Host: 1sat.app'  -H 'X-Forwarded-Proto: https' localhost:8100/.well-known/bsvalias   # endpoints on https://1sat.app
curl -s -H 'Host: 1sat.name' -H 'X-Forwarded-Proto: https' localhost:8100/.well-known/bsvalias  # endpoints on https://1sat.name
curl -s localhost:8100/bsvalias/id/<known-opns-name>@1sat.name      # 404 until that identity registers — expected
```

From a dev machine with a wallet, through a temporary host entry is not
needed: `1sat authfetch GET http://127.0.0.1:8100/account/status` over an
ssh tunnel (`ssh -L 8100:127.0.0.1:8100 ovh-n0001`) should return
`registrationEnabled: true, account: null` plus the storage fields.

## Phase 3 — shift traffic (the only moment that matters)

`/etc/nginx/sites-available/wallet.1sat.app` owns the upstream used by
`1sat.app`, `wallet.1sat.app`, `messagebox.1sat.app`.

Step 3a, overlap: add the cluster, keep the old forks and the hash.

```nginx
upstream wallet_backend {
    hash $http_x_bsv_auth_identity_key consistent;
    server 127.0.0.1:8100;
    server 127.0.0.1:8101;
    server 127.0.0.1:8102;
    server 127.0.0.1:8103;
    server 127.0.0.1:8104;
    keepalive 32;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
pm2 logs wallet-host --lines 50      # ~1/5 of traffic should show up here; watch for 5xx
```

Step 3b, cut over: after a few clean minutes, drop the old servers **and the
hash** (Redis makes it unnecessary; round-robin spreads load evenly).

```nginx
upstream wallet_backend {
    server 127.0.0.1:8100;
    keepalive 32;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

In-flight requests on 8101-8104 finish (graceful reload); new connections go
to the cluster. Wallet clients notice nothing: same DB, same Redis sessions.

Step 3c, monitor swap (seconds of gap, harmless). In `wallet.config.js`
change the `wallet-monitor` entry to the Node build:

```js
{
  name: "wallet-monitor",
  script: "/home/gorillapool/Code/1sat-cli/node_modules/@1sat/cli/dist/cli.js",
  args: "serve monitor",
  interpreter: "node",
  instances: 1,
  exec_mode: "fork",
  max_memory_restart: "1G",
  env: { NODE_ENV: "production", PATH, ...walletEnv },
},
```

```bash
pm2 delete wallet-monitor && pm2 start ~/pm2/wallet.config.js --only wallet-monitor
pm2 logs wallet-monitor --lines 20
```

## Phase 4 — retire the old forks

Wait a day (or until comfortable), then remove the four `wallet-server`
entries from `wallet.config.js` and:

```bash
pm2 delete wallet-server        # all four share the name
pm2 save
1sat-node config unset server.hosting     # or remove the block by hand
pm2 reload wallet-host                    # picks up the config drop, zero downtime
```

## Rollback (any point before Phase 4)

Put `8101-8104` (and the hash line) back in the upstream, `sudo nginx -t &&
sudo systemctl reload nginx`. The old forks never stopped. If they were
already deleted: `pm2 start ~/pm2/wallet.config.js.bak --only wallet-server`
(keep a dated `.bak` of the file before editing, as the earlier ones show). No data to undo: the only new table is
`accounts`, and nothing in the old code touches it.
