# StoragePg native port

Replace the thin `StoragePg extends StorageKnex` class with a native Postgres implementation that doesn't use knex. Port method-for-method from `StorageBunSqlite`.

## Why native, not knex

Audit of wallet-toolbox's `StorageKnex` against Postgres found unknown-unknowns across engine boundaries: insert RETURNING missing, bigint→string coercion, date/boolean read shape, MySQL-specific raw SQL in a few spots, plus `determineDBType` refusing Postgres entirely. The existing `StoragePg` (a thin subclass of `StorageKnex`) never ran end-to-end — first migration call threw `WERR_NOT_IMPLEMENTED` on engine detection.

Rather than fork wallet-toolbox to teach knex about Postgres (medium scope, unbounded edge-case risk), we port the sqlite implementation — which is already a clean drop-in of `WalletStorageProvider` — to a Postgres-native equivalent. Known cost, no ORM leakage, foundation for future BEEF-offload work.

## File

`packages/wallet-node/src/storage-pg.ts` — rewritten in place. Keep exported class name `StoragePg` so `createNodeWallet` wiring is unchanged.

## Schema translations

| SQLite | Postgres |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `BLOB` | `BYTEA` |
| `INTEGER` (used for bool 0/1) | `SMALLINT` with values 0/1 (preserve bun-sqlite semantics exactly) |
| `TEXT NOT NULL DEFAULT (datetime('now'))` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` |
| `?` placeholders | `$1, $2, ...` |
| `last_insert_rowid()` | `INSERT ... RETURNING <pk>` |
| `changes()` | `result.rowCount` |
| `PRAGMA table_info(t)` | `information_schema.columns WHERE table_name = $1` |
| `PRAGMA foreign_keys = OFF/ON` | not needed; create tables in dependency order |
| `datetime('now')` | `NOW()` |

**Booleans stored as SMALLINT 0/1 rather than native BOOLEAN** — preserves byte-for-byte semantics with `StorageBunSqlite.validateEntityForInsert` / `validatePartialForUpdate` which convert `true/false` → `1/0`. Moving to native BOOLEAN would require overriding those validators, creating behavioral drift risk.

**Dates**: columns use `TIMESTAMPTZ`. Driver returns `Date` objects on reads, accepts `Date` on writes. Our validate overrides pass `Date` through instead of ISO-stringifying like bun-sqlite does.

## Parity discipline

Preserve all labeled semantic fixes from StorageBunSqlite history:

- **CRIT-4**: `findOutputs`/`countOutputs` accept `tagIds` + `isQueryModeAll`; `findTransactions`/`countTransactions` accept `labelIds` + `isQueryModeAll`. Apply via EXISTS (any) or COUNT=N (all) subqueries.
- **HIGH-7**: `listOutputs` status filter includes `'sending'`.
- **HIGH-8**: orphan map rows tolerated via `verifyOneOrNone` + skip, not error.
- **HIGH-11**: batch updates return row count, don't throw on missing.
- **HIGH-12**: `countProvenTxReqs` mirrors `findProvenTxReqs` filters (status + txids).
- **HIGH-13**: `findOrInsert*` threading — inherited from base class but confirm trx propagation.
- **MED-14**: `allocateChangeInput` calls `validateOutputScript` on the chosen output only.
- **MED-15**: `recentlyActiveUsers` = SQL-backed JOIN + GROUP BY, not base-class scan.
- **MED-16**: `listOutputs` negative offset → DESC + reindex.
- **MED-18**: `findTransactions({noRawTx})` strips `rawTx` only, keeps `inputBEEF`.
- **MED-19**: `insertCertificate` strips non-schema fields (e.g., `logger`) via `filterToSchema`.
- **LOW-23**: `updateRows` reads `rowCount` once.
- **LOW-26**: `listOutputs` gates COUNT query on `outputs.length >= limit`.
- **LOW-27**: `validateOutputScript` debug-logs when hydration impossible.
- **LOW-28**: `getRawTxOfKnownValidTransaction` slice path uses `'unfail'`-inclusive status set.

Plus StorageIdb-era fixes that apply to any port:
- **CRIT-1**: `internalizeAction` writes `scriptOffset`/`scriptLength`; `findOutputs(noScript=true)` doesn't strip script.
- **CRIT-2**: `updateTransactionStatus('failed')` unspends own outputs atomically.

Most of these live in the base `StorageProvider`/`StorageReader` classes and are inherited. The port must not override them in ways that reintroduce the drift.

## Transaction model

`pg.Pool` wrapped. `transaction<T>()` checks out a single `PoolClient`, issues `BEGIN`, runs scope with a trx token that carries the client, `COMMIT` on success / `ROLLBACK` on error. Nested `transaction()` calls use `SAVEPOINT` within the existing client (matching bun-sqlite's savepoint-on-same-connection model).

`toDb(trx)` returns either the trx's pooled client or the pool itself. Queries route through whichever the caller passed.

## Binary parameters

pg accepts `Buffer` directly for `bytea`. `Uint8Array` and `number[]` convert via `Buffer.from(val)`. Same semantics as bun-sqlite's `toBlob` helper.

## Parameter binding

Sqlite `?` is a positional placeholder. Postgres uses `$1, $2, ...`. Every query needs translation. Options:

- **Option A**: hand-translate each query to `$n` style.
- **Option B**: helper that rewrites `?` → `$n` as params are bound.

Going with **B** — one helper at the query-execution layer (`runSql`/`allSql`/`getSql`), everything else writes `?` and stays diffable against `StorageBunSqlite`.

## DBType labeling

Settings row stores `dbtype: 'Postgres'`. The wallet-toolbox `DBType` union doesn't include it; we'll cast. Our date-validation overrides mean the base `StorageReader` switches never see this value. If any base-class path does inspect `dbtype` and throws on Postgres, handle per-case.
