# StoragePg → StorageKnex: production database migration

Converts the production wallet database `account_wallet` (Postgres 16, reached through HAProxy
localhost:5000 on ovh-n0001) from the schema built by `1sat-sdk/packages/wallet-node`
`StoragePg` to the schema `@bsv/wallet-toolbox` `StorageKnex` builds on Postgres
(ts-stack branch `feat/storageknex-postgres`, PR bsv-blockchain/ts-stack#719).

Rehearsed on 2026-10-01 against a fresh `pg_dump -Fc` of production (1.99 GB dump, 2.6 GB restored),
restored into a local Postgres 17.10 cluster.

## Prerequisites

- A released toolbox with Postgres support that includes ts-stack commit `1a98f8eb5`
  (paged queries ordered by key, see "Sync paging" below).
- A 1sat wallet server build that opens this database with `StorageKnex` and calls `migrate` on
  startup (`createNodeWallet` does).
- The conversion and the code switch happen in the same maintenance window. The script turns 13
  `smallint` columns into `boolean`; StoragePg's raw SQL (`spendable = 1`, ...) fails against them.

## Files

| File | Purpose |
|---|---|
| `1sat-sdk/scripts/migrations/2026-10-01-storagepg-to-storageknex.sql` | The conversion. One transaction, idempotent. |
| `1sat-sdk/scripts/migrations/storageknex-schema-describe.sql` | Prints one sorted line per table, column, constraint, index and sequence. |
| `1sat-sdk/scripts/migrations/2026-10-01-storageknex-schema.expected.txt` | Its output for an empty database migrated by StorageKnex (branch build, 26 migrations). |

## Schema differences and what the script does

Production compared with an empty StorageKnex database, table by table (16 shared tables).

| Difference | Production (StoragePg) | StorageKnex | Script |
|---|---|---|---|
| 13 flag columns (`outputs.spendable`, `outputs.change`, `transactions.isOutgoing`, `proven_tx_reqs.notified`/`wasBroadcast`, `sync_states.init`, `commissions.isRedeemed`, `isDeleted` on 6 tables) | `smallint`, default `0` | `boolean`, default `false` | `TYPE boolean USING col <> 0` |
| 51 string columns | `text` | `varchar(n)` (txid 64, identityKey 130, description 2048, ...) | `TYPE varchar(n)`. Assignment cast: a longer value aborts the transaction. Longest production values are well inside every limit. |
| `created_at`/`updated_at` (32 columns) | `timestamptz`, default `now()` | `timestamptz(3)`, default `CURRENT_TIMESTAMP` | `USING date_trunc('milliseconds', col)`. node-postgres already drops sub-millisecond digits, so clients see the same values as before. Sync filters use `>=`, which truncation preserves. |
| 12 primary keys | `integer GENERATED BY DEFAULT AS IDENTITY` | `serial` (`"<table>_<col>_seq"`) | `DROP IDENTITY`, create the knex-named sequence, set the default, continue from the identity sequence's position. |
| `commissions.satoshis` | `bigint` | `integer` | `TYPE integer` (table is empty in production) |
| `transactions.description` | `NOT NULL` | nullable | `DROP NOT NULL` |
| `users.activeStorage` | nullable | `varchar(255) NOT NULL` | `SET NOT NULL` (no NULLs in production) |
| `output_baskets` defaults | 6 / 10000 | 144 / 5000 | `SET DEFAULT` |
| `transactions.satoshis` default | `0` | `'0'::bigint` | `SET DEFAULT` |
| 34 unique and foreign key constraints | Postgres names (`outputs_userId_fkey`, `..._key`) | knex names (`outputs_userid_foreign`, `..._unique`) | `RENAME CONSTRAINT` |
| 13 indexes | short names (`outputs_spendable`) | knex names (`outputs_spendable_index`) | `ALTER INDEX ... RENAME` |
| `outputs_userid`, `transactions_userid` | present (StoragePg-only migrations 2026-04-20-001/002) | absent | Dropped. `userId` leads `idx_outputs_user_spendable_outputid` and `idx_transactions_user_proven_tx`. |
| `sync_states_user_storage_identity` unique (`userId`, `storageIdentityKey`) | present (StoragePg-only 2026-09-30-001) | absent | **Kept.** It turns the `findOrInsertSyncStateAuth` insert race into a constraint error that the toolbox retries as a find. This is the only difference left after migration. |
| `knex_migrations` | 22 rows, 4 not known to the toolbox | 26 rows | Deletes the 4 StoragePg-only rows; StorageKnex refuses to run while they exist. |
| 10 tables (action batches, prepared BEEF, auth sessions/nonces, payment replays, sync transfers) | absent | present | Not touched. `StorageKnex.migrate` creates them. |
| `settings.dbtype` | `Postgres` | `Postgres` | Sets it if different. |

Same on both sides: column names, PKs, unique/FK column sets, binary columns (`bytea`), the
`knex_migrations` and `knex_migrations_lock` tables. `settings` keeps its row
(`storageIdentityKey 1sat-cli-ea25dc952d4effc0`, `storageName wallet`).

After the script, `StorageKnex.migrate` applies the 8 toolbox migrations StoragePg never had: 7 create
the new tables, and `2026-08-10-001 upgrade managed change liquidity defaults` sets
`minimumDesiredUTXOValue` from 32 to 5000 on every `default` basket that still has 144/32 (1903 of
1957 in the rehearsal) and bumps their `updated_at`, so the change syncs to clients.

## Measured duration (full production data, local rehearsal)

| Step | Time |
|---|---|
| Conversion script, incl. `ANALYZE` | 18.0 s, 20.1 s, 33.0 s (three runs). `proven_tx_reqs` (1.8 GB) is 60–75% of it. |
| `StorageKnex.migrate` (8 migrations) | 0.06 s |
| `StorageKnex.migrate` again | 0.02 s, applies nothing |
| `pg_dump -Fc` of production, streamed over SSH | 3 min 40 s |
| `pg_restore -j 8` of that dump | 28 s locally (the rollback restore is single-threaded) |

The rehearsal ran on a laptop NVMe with Postgres 17. Production is Postgres 16 with one async replica;
the script uses no 17-only features but was not run on 16. Budget 2 minutes for the script. The
rewrite produces roughly 2.5 GB of WAL.

## Procedure

1. Stop every process that connects to `account_wallet` (the `1sat` server instances and the monitor).
   Confirm nothing is left:

   ```sql
   select pid, usename, application_name, client_addr, state
   from pg_stat_activity where datname = current_database() and pid <> pg_backend_pid();
   ```

2. Take the rollback dump and record row counts (`counts.sql` is the row count query under
   Verification):

   ```bash
   DB_URL="$(jq -r .server.storage.dbUrl ~/.1sat/cli/config.json)"
   mkdir -p ~/predeploy-backups/$(date +%Y%m%d)
   pg_dump -Fc "$DB_URL" -f ~/predeploy-backups/$(date +%Y%m%d)/account_wallet.pre-storageknex.dump
   psql "$DB_URL" -Atf counts.sql > counts.before
   ```

3. Run the conversion as the table owner (`onesat`, the dbUrl role):

   ```bash
   psql "$DB_URL" -v ON_ERROR_STOP=1 -f 2026-10-01-storagepg-to-storageknex.sql
   ```

   It prints one `altered <table> in <ms>` line per table. Any error rolls everything back; the
   database is then unchanged and the old server can be started again. `lock_timeout` is 10 s, so a
   leftover connection makes it fail rather than wait.

4. Start the wallet server on the StorageKnex build. Its startup `migrate` applies the 8 toolbox
   migrations.

5. Verify (below), then watch the server logs.

## Verification

```sql
-- 26 journal rows, none of the StoragePg-only names
select count(*) from knex_migrations;
select name from knex_migrations where name in (
  '2026-04-20-001 add transactions userId index', '2026-04-20-002 add outputs userId index',
  '2026-09-30-001 unique sync state per storage identity', '2026-09-30-002 re-file legacy p 1sat baskets');

-- no smallint or identity columns left
select table_name, column_name, data_type, is_identity from information_schema.columns
where table_schema = current_schema() and (data_type = 'smallint' or is_identity = 'YES');

-- every sequence at or past its column's maximum
select c.relname as seq, pg_sequence_last_value(c.oid) as last_value,
  (xpath('/row/m/text()', query_to_xml(format('select max(%I) as m from %I', a.attname, t.relname),
    false, true, '')))[1]::text::bigint as max_id
from pg_class c
join pg_depend d on d.objid = c.oid and d.classid = 'pg_class'::regclass and d.deptype = 'a'
join pg_class t on t.oid = d.refobjid
join pg_attribute a on a.attrelid = t.oid and a.attnum = d.refobjsubid
where c.relkind = 'S' and c.relnamespace = current_schema()::regnamespace order by 1;
```

## Rollback

`2026-10-01-storageknex-deploy.sh rollback` stops both apps, restores the dump if the database is
converted, puts back the saved install and `config.json`, and starts them again.

- Script failed: nothing changed. Start the StoragePg build.
- Script committed: restore the dump from step 2 in place. In one transaction, drop every table and
  sequence in the schema, then replay the dump:

  ```bash
  { echo 'BEGIN;'
    echo 'DROP TABLE <every table in the schema>;'
    echo '<DROP SEQUENCE for every sequence in the schema>'
    pg_restore -f - ~/predeploy-backups/<date>/account_wallet.pre-storageknex.dump
    echo 'COMMIT;'
  } | psql "$DB_URL" -X -q -v ON_ERROR_STOP=1
  ```

  Then `ANALYZE`, check `knex_migrations` is back to 22 rows and `counts.sql` matches `counts.before`.
  Any error rolls the whole restore back and leaves the converted database as it was. The restore is
  single-threaded; it took 28 s locally with `-j 8`, budget 10 minutes in production.

  Two alternatives do not work. `pg_restore --clean --if-exists` fails on the converted schema: the
  renamed foreign keys (`outputs_userid_foreign` and others) and the new toolbox tables block dropping
  `users_pkey` and `users`. Restoring into a new database and swapping names needs CREATEDB or
  superuser, and the `onesat` role has neither.
- There is no reverse script. Writes made by the StorageKnex server after cutover are lost by a restore.

## Rehearsal results

- Script then `StorageKnex.migrate`: schema identical to `2026-10-01-storageknex-schema.expected.txt`
  except the kept index; `knex_migrations` names identical to a fresh StorageKnex database; a second
  `migrate` applied nothing; re-running the script changed nothing.
- Reads, StorageKnex on the converted copy against StoragePg (git HEAD `d419a147`) on an unconverted
  copy, for 5 users (61,930 / 2,685 / 636 / 171 / 43 outputs; one with certificates):
  `findOrInsertUser`, `listOutputs` per basket and by tag (incl. `entire transactions` BEEF),
  `listActions` (all, and by label), `listCertificates`, `getProvenOrRawTx`, `getBeefForTransaction`,
  `findProvenTxs`/`findProvenTxReqs`, a full `getSyncChunk` walk (up to 427 pages) and a walk from a
  mid-point `since`. All rows of all 12 sync entities were identical; the only differences were the
  `default` baskets changed by the managed-change migration, and tag/label order inside list
  results, which neither engine sorts.
- Writes through StorageKnex: new user, basket, tag, label and monitor event got ids past the
  migrated maxima; two concurrent `findOrInsertSyncStateAuth` calls produced one row; a duplicate
  basket was rejected; `createAction` funded from a real user's change (5 inputs locked, 2 outputs)
  followed by `abortAction` left the action `failed` and the user's spendable set unchanged.
- ts-stack wallet-toolbox jest suite with `RUNPOSTGRES=1`: 290 suites, 3129 tests passed.

## Sync paging (fixed on the branch, present in production today)

Paged sync queries (`getProvenTxsForUser`, `getProvenTxReqsForUser`, `getTxLabelMapsForUser`,
`getOutputTagMapsForUser`, and paged `find*`) had no `ORDER BY`, in StoragePg and in StorageKnex.
Postgres does not keep row order across LIMIT/OFFSET queries without one, so `getSyncChunk` repeated
some rows and skipped others. On the rehearsal data, a full sync of the largest wallet from StoragePg
skipped 42,359 of 237,526 output tag maps, 1,125 of 9,524 label maps and 51 of 2,372 proven txs.
ts-stack commit `1a98f8eb5` orders those queries by key; StorageKnex with it delivered every row.

Clients that synced from the production StoragePg server may be missing rows. Incremental (`since`)
sync does not resend them; only a full resync of an affected client does.
