# Toolbox 2.6.2 → 2.14.4: storage engine and server contract

Scope: what `@bsv/wallet-toolbox` / `@bsv/wallet-toolbox-client` 2.14.4 requires of a third-party
storage engine (`1sat-sdk/packages/wallet-node` `StoragePg`, `StorageBunSqlite`) and a third-party
storage server (`1sat-sdk/packages/wallet-server`), compared with the `@bopen-io` 2.6.2-brc153.5 fork
those were written against. Research only; nothing was changed.

Baseline: 1sat-sdk master `d2752537` (wallet-node 0.0.80, wallet-server 0.0.57, cli 0.0.123).
Paths below are relative to `~/Source/1sat`.

Evidence labels:
- **[code]** read in source/tarball.
- **[run]** reproduced locally (`bun -e` against `StorageBunSqlite` on `:memory:`, toolbox 2.14.4).
- **[inferred]** follows from code but not executed (e.g. Postgres, which uses the same code path as SQLite).

Sources: npm tarballs of `@bsv/wallet-toolbox` 2.6.2 / 2.12.0 / 2.14.4 and `@bsv/wallet-toolbox-client`
2.6.2 / 2.12.0 / 2.13.1 / 2.13.2 / 2.14.4 (scratchpad), ts-stack `origin/main` history
(`packages/wallet/wallet-toolbox`), toolbox `CHANGELOG.md` delta 2.6.2 → 2.14.4.

Conclusion for §1: with the current code, **`dbtype` is the only response-contract failure** a 2.14.4
client hits against wallet-server 0.0.57. Against the current production server (cli 0.0.87 era) the
void-`result` omission also fails, for `destroy`.

`dbtype` is used by the toolbox only on the provider itself for date handling
(`StorageReader.js` `dbtype` switch); the client never reads the remote value except in the validator.
Upstream's own server already rewrites settings on the wire (adds `syncCheckpointVersion`) without
touching the row (`StorageServer.js#L679-687`, 2.14.4). Options:
- A. Rewrite `dbtype` in the `makeAvailable`/`getSettings` RPC response (wire only).
- B. Omit `dbtype` in the RPC response (validator accepts absent).
- C. Change the persisted row (and `StoragePg` INSERT) to an allowed value.
Decision needed; A or B leaves the DB untouched.

**Allowlist gap (Critical, pre-existing).** `dispatch()` accepts any method name for which
`typeof storage[method] === 'function'` (`dispatch.ts#L55`). `storage` is the active `StoragePg`
(`cli/src/commands/serve.ts#L393,L432` → `wallet/src/factory.ts#L498`). Reachable examples:
`dropAllData` (`storage-pg.ts#L917`, drops every table), `purgeData`, `findUsers`, `findTransactions`,
`findOutputs` (all users), `updateUser` (change another user's `activeStorage`), `insertProvenTx`,
`updateOutput`. The only gate is BRC-103 authentication, which any key pair satisfies. Upstream
restricted dispatch to the public protocol in 2.6.x ("Restrict JSON-RPC dispatch to the public
remote-storage protocol…"; ts-stack `2acbbbc3f`, 2026-07-24). This exists in production today and is
independent of the toolbox upgrade.

**auth binding gap (High, pre-existing).** `applyParam0Auth` (`dispatch.ts#L130-153`) overwrites
`userId` only when the caller put `identityKey` in param0 (`#L150-152`). A param0 of `{ userId: N }`
without `identityKey` passes through, and storage methods use `auth.userId` directly (e.g. base
`abortAction` `StorageProvider.js#L479-481`, engine `findOutputsAuth` `storage-pg.ts#L2907-2912`).
Upstream always overwrites (`validateParam0` `StorageServer.js#L879-894`: `if (identityKey || userId != null)`)
and, for auth-id methods, rebuilds param0 from the server's own lookup including `isActive`
(`bindAuthenticatedAuth` `#L864-878`). Our server passes the client's `isActive` claim through.

## 3. StorageProvider base changes that engines must satisfy

### 3.1 Abstract surface

No new `abstract` members between 2.6.2 and 2.14.4 (diff of `StorageProvider.d.ts`,
`StorageReaderWriter.d.ts`, `StorageReader.d.ts`). Only type-import changes
(`Validation.Valid*Args` → `@bsv/sdk/wallet/validationHelpers`). The engines compile, which hides the
runtime breakage below.

### 3.2 Schema: `transactions` BRC-177 columns — **Critical**

`TableTransaction` gains 13 fields (`noSendExpiryMode, …Value, …Deadline, …State, …AnchorTxid,
…AnchorVout, …ReleasedAt, …ObservedAt, …ReclaimTxid, …ReclaimRawTx, …ReclaimDerivationPrefix,
…ReclaimDerivationSuffix, …ReclaimSatoshis`), Knex migration `2026-08-30-001 add brc177 nosend expiry
state` (`KnexMigrations.js`, 2.14.4) with indexes `idx_transactions_nosend_expiry
(noSendExpiryState, noSendExpiryDeadline)` and `idx_transactions_nosend_reclaim (userId,
noSendExpiryReclaimTxid)`. Introduced ts-stack `f5a37680d` (2026-08-30), first published ~2.11.

The exported column list the engines use for `noRawTx` reads now includes 12 of them
(`transactionColumnsWithoutRawTx`, `schema/tables/TableTransaction.js`, 2.14.4). Both engines build
their SELECT from it:
- `StoragePg.findTransactions` `storage-pg.ts#L2630-2634`
- `StorageBunSqlite.findTransactions` `storage-bun-sqlite.ts#L2341`

Neither engine has the columns (no BRC-177 migration in `storage-pg.ts#L457-903` or
`storage-bun-sqlite.ts`). Result [run, SQLite]:

```
findTransactions noRawTx   ERR no such column: transactions.noSendExpiryMode
updateTransactionStatus    ERR no such column: transactions.noSendExpiryMode   (unproven and failed)
updateTransactionsStatus   ERR no such column: transactions.noSendExpiryMode
abortAction                ERR no such column: transactions.noSendExpiryMode
findTransactions (full)    OK
listActions                OK   (engine's own query)
```

Base call sites with `noRawTx: true` (2.14.4 `StorageProvider.js`): `findAbortableTransaction`
(L415, L422), `abortAction` (L592), `protectNoSendExpiryReclaimInputOnFailure` (L760, which also
filters on `noSendExpiryReclaimTxid`), `updateTransactionStatus` (L796),
`unfailTransactionsForProof` (L1254, L1276); plus `methods/reconcileFailedTransactionInputs.js`.
`updateTransactionStatus` is reached from `updateTransactionsStatus`, which is how
`attemptToPostReqsToNetwork` records every broadcast outcome (`methods/attemptToPostReqsToNetwork.js#L246`),
`TaskFailAbandoned`, `TaskArcadeSSE`, `TaskReconcilePendingTransactions`, and createAction failure
cleanup (`methods/createAction.js#L210`).

Affected releases: wallet-node 0.0.80 and everything built on it — cli 0.0.123 local wallets
(`StorageBunSqlite`) and any `1sat serve` on it (`StoragePg`). Remote-active clients against such a
server break too, because broadcast status is recorded server-side in `processAction`. Production
(cli 0.0.87, fork base) is not affected until upgraded. Postgres is [inferred]: identical code path,
quoted identifiers, same missing columns.

`buildWhere` passes unknown keys straight into SQL (`storage-pg.ts#L1046-1073`), so partial filters on
new columns error rather than being ignored; `insertRow`/`updateRows` instead drop unknown keys via
`filterToSchema` (`storage-pg.ts#L429-440`, `#L1254`), so writes of these fields are silently lost.

### 3.5 Monitor

2.14.4 `addDefaultTasks` adds `TaskNoSendExpiry` (every 5 s) and `TaskReconcilePendingTransactions`
(`monitor/Monitor.js#L213-215`). `TaskNoSendExpiry` → `processNoSendExpiryLifecycle` →
`findTransactions({ partial: { noSendExpiryState } })` (`methods/noSendExpiryLifecycle.js#L666-679`) →
SQL error on our engines; `runScheduledTask` logs every failure as an `error1` row via
`insertMonitorEvent` (`Monitor.js#L347-371, L397-410`). With `taskRunWaitMsecs: 5000`
(`wallet/src/factory.ts#L319`) that is ≈17k rows/day per monitor. `1sat serve` runs this monitor in
`monitor` and `all` modes (`cli/src/commands/serve.ts#L292-305`). Fixed by §3.2's migration.

## 4. Sync semantics (yours-wallet IndexedDB ↔ wallet-server)

| Topic | 2.14.4 behaviour | Impact on our server |
|---|---|---|
| Checkpoint | Client asks writer for compact checkpoint only if `syncCheckpointVersion === 1`; otherwise `EntitySyncState.fromStorage` → `findOrInsertSyncStateAuth` (`WalletStorageManager.js#L718-731`) | Legacy path works; compact path needs only an allowlist entry + settings flag (base implements it) |
| Page args | Every page carries `includeNextCheckpoint: true`; adaptive `SyncPageBudget` starting at `maxItems 64` | Our base `processSyncChunk` returns `nextCheckpoint`; client validates it (§1) |
| Page atomicity | Page data and `sync_states` update in one provider transaction | Uses `StoragePg.transaction()`; OK |
| Proof validation (RPC) | Upstream server validates every incoming `provenTxs` row against the chain tracker before `processSyncChunk` (`StorageServer.js#L797`, `remoting/validateRpcSyncProofs.js`, ts-stack `70048bafc`) and runs `validateSyncChunkEntities` | **Missing.** Our server only normalises dates/buffers (`dispatch.ts#L155-203`). `proven_txs` is global by txid, so an authenticated caller can insert a bogus proof for a txid before the real one arrives; other users' later proof completion finds the existing row ("someone beat us to it", `StorageProvider.js#L1052-1058`) [inferred] |
| Transactions with BRC-177 fields | Sync chunks from a 2.14.4 IDB include the 13 fields for BRC-177 actions (`syncChunkBinary.js` lists `noSendExpiryReclaimRawTx` as binary) | Dropped on insert/update (`filterToSchema`) until columns exist; the pre-signed reclaim is lost on the server copy |
| Output-basket mapping | Client rejects pages whose outputs reference an unmapped basket | Our `getSyncChunk` is the base implementation → consistent |
| Totals | Optional `includeTotals`; base default returns none | Fine |
| Oversized pages | Sync transfer (64 MiB frames) only when advertised; otherwise 413 retry for reads | Our `express.json` limit is 30 MB (`createWalletServer.ts#L98`); processSyncChunk pages start small |
| IDB schema v6 | Client-side; "clients requesting schema version 5 cannot open the upgraded database" | Not a server concern; means yours-wallet cannot roll back from a 2.14.x build to 2.12.0 on the same profile |

Upstream open PR #569 (draft, "Hold open: do not merge") adds retained-reader SQL sync, an auxiliary
migration `2026-09-30-002` and archive capture. Excluded here; it would add more tables for SQL
providers if merged.

   methods (no custom RPC names found in `1sat-sdk/packages`, `yours-wallet/src`); keep `adminStats`
   and `getSettings`.
3. `findOrInsertSyncStateAuth` duplicate rows — run before upgrading (read-only):
   `SELECT "userId","storageIdentityKey",count(*) FROM sync_states GROUP BY 1,2 HAVING count(*)>1;`
   Any hit fails sync for that user with `WERR_INVALID_OPERATION` unless one row's `storageName`
   matches exactly.
4. Managed-change migration, if applied, changes `default` basket `minimumDesiredUTXOValue` 32→5000
   and bumps `updated_at`, which then syncs to clients. New users already get 5000 via the base code.
   Decision whether to migrate existing rows.

Production Postgres (`account_wallet`) migrations implied:
- `ALTER TABLE transactions ADD COLUMN …` ×13 (all nullable) + 2 indexes. Nullable `ADD COLUMN` is
  metadata-only in Postgres; indexes on a large `transactions` table should be built
  `CONCURRENTLY` or off-peak.
- `ALTER TABLE proven_tx_reqs ADD COLUMN "wasBroadcast" SMALLINT NOT NULL DEFAULT 0,
  ADD COLUMN "rebroadcastAttempts" INTEGER NOT NULL DEFAULT 0` (constant defaults are metadata-only
  on PG 11+).
- Optional indexes from §3.3.
- The old server (cli 0.0.87) keeps working against the migrated schema: it reads with `SELECT *`
  and filters writes to existing columns; extra nullable columns are ignored [inferred]. So the DB
  can be migrated before the new server is deployed.
